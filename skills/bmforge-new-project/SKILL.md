# BMForge greenfield bootstrap

This is the **user-level** skill. Install it once under `~/.agents/skills/bmforge-new-project/` (or through Codex's skill installer), then invoke it from a **new destination Git repository**. DevLog is a mental size/architecture example, not an installation target unless the user explicitly asks.

1. Discuss only the requirements needed to choose components. Never select everything by default. The available project-local component skill names are `bmforge-http`, `bmforge-zmq`, `bmforge-db-server`, `bmforge-git`, `bmforge-visualization`. The `bmforge-project`, `bmforge-constants`, `bmforge-localization`, and `bmforge-installation` baseline skills are always included. An empty initial selection is valid.
2. Ask permission to initialise the destination repository if the user has not given it. Do not run `git init`, make application classes, create a DB, bind ports, or deploy services. Use the existing repository root.
3. Run `python3 <this-skill>/scripts/manage.py init --project <repo-root> --name <CanonicalAppName> --components bmforge-http,bmforge-db-server` with **only the user-selected** component names. The example is not a default selection. The script clones the current BMForge `main` into a disposable directory and pins a snapshot of each selected skill. For local testing only, pass `--source /path/to/bmforge`.
4. Ask for the canonical Python application name (e.g. `SnakeLab`, package `snakelab`) and optional CMDB subtype. Require `--name`; repository names do not always match Python package names.
5. Install pinned skills and project instructions. Also use the **existing BMForge release templates** to generate `scripts/new-release.sh`, the CMDB checker, lifecycle scripts, version constants and `CHANGELOG.md`. Fill in project name, slug and subtype. Refuse to overwrite files or follow symlinked target directories.
6. File generation does **not** authorise release execution: do not automatically commit, push, tag, deploy, or enable installation. **After the user reviews and commits the scaffold on local `main`**, offer a separate branch-setup step using `python3 .agents/bmforge/manage.py setup-branches --project . --dry-run`. With explicit approval, run `setup-branches` to create **local** `dev` and `feat/maint-0.1.0` (or the approved `--feature` name). Refuse dirty, unborn, non-`main`, diverged or pre-existing branch states. Never create remote refs or push automatically. When the application has defined requirements, use the mandatory `bmforge-installation` skill to implement and test **install, upgrade and uninstall**. Even a library-only or client-only installation must have an owned, versioned `/opt/prod` directory. Create `install-server.sh` only for an explicitly required separate server role.
7. To select additional components later, use `python3 .agents/bmforge/manage.py add --project . --components <names>`. This refuses to overwrite existing installed skills.
8. Before a new Codex work session changes BMForge-derived application code, run `python3 .agents/bmforge/manage.py check --project .`, **report updates**, and **never apply an update without direct user approval**. The check reports per-skill changes and local modifications, and does not write to the project. If offline, explain that updates could not be checked and continue only using pinned skills.
9. There is intentionally no implicit `upgrade` operation. If the user approves an update, follow an explicit, separately reviewed update workflow preserving local changes, commit history and the lock. Never copy a new version merely because the checker detected it.

The script requires Python 3 and Git. Codex discovers installed project-local skills from `<repo>/.agents/skills`. The specification and reference code are packaged within each installed skill; the destination application never imports BMForge at runtime.
