# DB Server

**Ідентифікатор компонента:** `{{ page.component_id }}` · **Специфікація:** `{{ page.spec_version }}` ({{ page.spec_status }})

Цей контракт дотримується [інженерної політики]({{ site.baseurl }}{% link uk/pages/engineering-contract.md %}), [контракту перевірок працездатності]({{ site.baseurl }}{% link uk/pages/health-checks.md %}) і [правил простежуваності]({{ site.baseurl }}{% link uk/pages/specification-lifecycle.md %}).

## Призначення та обсяг

Надайте мінімальний рівень доступу до бази даних, яким володіє застосунок, на MariaDB через PyMySQL. Це доступ до даних із боку застосунку, а не керування демоном MariaDB. Відокремлюйте механіку з’єднань і SQL-виконання від схеми та запитів застосунку. Не вводьте ORM, глобальний пул з’єднань, фреймворк міграцій або віддалену службу без конкретної вимоги.

## Схвалені модулі виконання

Це **повний перелік схвалених модулів канонічного повторно використовуваного `DbMgr.py`** у специфікації `0.4.0`.

| Походження | Модуль | Призначення |
| --- | --- | --- |
| Стандартна бібліотека Python | `contextlib` | `contextmanager` для коміту й відкату транзакцій |
| Сторонній | `pymysql` | З’єднання MariaDB, прив’язаний SQL, запити й транзакції |
| Підмодуль стороннього пакета | `pymysql.cursors` | `DictCursor` для рядків-словників (частина PyMySQL, а не інший пакет) |

**Межа схвалення:** канонічний `DbMgr.py` **копіюється без змін** у кожен застосунок, який використовує MariaDB; його методи, імпорти та назва класу не налаштовуються. Передавайте конфігурацію застосунку в конструктор і створюйте окремі предметні інтерфейси `*Db` для SQL. Codex **має зупинитися й запитати користувача** перед додаванням, видаленням або заміною схваленого інфраструктурного модуля чи зміною `DbMgr.py`. Схвалені зміни повинні входити до нової специфікації BMForge перед застосуванням.

Це модулі імпорту Python, а не повне дерево транзитивних залежностей. Файл залежностей застосунку містить установлені версії пакетів. Предметна логіка й окремо вибрані компоненти BMForge не входять до цього списку та не можуть непомітно змінювати технології компонента.

**Технологія бази даних:** MariaDB. Не замінюйте її на PostgreSQL, SQLite, SQLAlchemy, Peewee, mysql-connector, ORM, інший драйвер або зовнішню службу бази даних. Інший бекенд потребує нової специфікації компонента та схвалення користувача.

**Не входять до загального менеджера:** `GeoIpDb`, `VisitDb`, `MiningDb`, `GeoIpSource`, визначення схем і SQL застосунку. Вони належать до **предметних інтерфейсів** застосунку-споживача. Дивіться [Класифікацію Activity / Interface / Entity]({{ site.baseurl }}{% link uk/pages/classification.md %}).

## Канонічна реалізація й рівні DAL

**Кожен новий застосунок із MariaDB копіює той самий файл без змін:**
`components/templates/db-server/interface/DbMgr.py` → `<app>/interface/DbMgr.py`.

Конфігураційний інтерфейс застосунку визначає секрети, дані з’єднання й тайм-аути та передає їх як іменовані аргументи конструктора. **Не імпортуйте константи застосунку, схему чи зчитувачі середовища в канонічному менеджері.** Він надає універсальні `execute`, `insert`, `execute_many`, `query`, `transaction(read_only=False)`, `health`, `close` і очищення через контекстний менеджер.

Над `DbMgr` застосунок визначає один або більше **предметних інтерфейсів бази даних**, наприклад `VisitorDb`, `MiningDb` чи `GeoIpDb`. Кожен отримує екземпляр `DbMgr` через конструктор. Вони володіють SQL, схемою, перетворенням рядків на сутності та згрупованими записами. Вони ніколи не викликають `pymysql.connect` і не керують курсорами безпосередньо. Кілька предметних класів можуть спільно використовувати один `DbMgr` у межах одного потоку-власника/транзакції, **але не між потоками**. Створення бази даних та міграції предметних даних залишаються окремими операціями.

Наприклад, споживач може реалізувати:

```python
class VisitorDb:
    def __init__(self, db: DbMgr):
        self._db = db

    def count(self):
        return self._db.query("SELECT COUNT(*) AS visits FROM page_views")[0]["visits"]
```

Клас `activity/CollectVisit.py` викликає іменовані операції `VisitorDb` і працює зі значенням `entity/Visit.py`. SQL не повинен з’являтися в активностях, сутностях, шаблонах або транспорті HTTP/ZeroMQ. Це звичайна композиція, а не успадкування чи ORM. Дивіться [контракт класифікації]({{ site.baseurl }}{% link uk/pages/classification.md %}).

**Інтеграція нового проєкту:** скопіюйте `DbMgr.py` без змін, передайте визначену конфігурацію, створіть лише потрібні предметні інтерфейси `*Db` і сутності та протестуйте транзакції й перевірки стану. Наявні застосунки не потребують автоматичної міграції лише через зміну цієї чернетки специфікації.

## Еталонний знімок

- `components/reference/bmgeoip/bmgeoip/interface/DbMgr.py`: історична версія механіки, **не** канонічний файл для копіювання (імпортує константи BMGeoIP).
- `components/reference/bmgeoip/bmgeoip/interface/DatabaseEnvironment.py`: спеціалізоване читання конфігурації BMGeoIP; нові застосунки окремо визначають власні налаштування.
- `components/reference/bmgeoip/bmgeoip/interface/GeoIpDb.py`: SQL та схема застосунку в предметному інтерфейсі.
- `components/reference/mycount/mycount/interface/VisitDb.py`: інший предметний інтерфейс з `DbMgr`, закріплений із MyCount на коміті `90574cd838ba43499a825c6a193b43cbc485c91c`.

## Обов’язковий контракт

- **Незмінний канонічний `DbMgr.py`** володіє одним з’єднанням MariaDB, створеним із визначеної конфігурації застосунку, та детерміновано закриває його. Застосунок передає хост/порт БД чи сокет, назву схеми, облікові дані й тайм-аути під час створення. Не діліться одним менеджером між робочими потоками.
- Визначайте й перевіряйте зовнішню конфігурацію з’єднання в інтерфейсі застосунку **до** створення `DbMgr`; не додавайте читання конфігураційних файлів чи константи застосунку до менеджера. Жодних секретів у коді, публічній документації, повідомленнях про стан або HTTP-відповідях.
- Використовуйте utf8mb4, результати-словники за потреби, явні тайм-аути підключення/читання/запису та суворий режим SQL згідно з еталоном.
- Використовуйте канонічні методи: параметризований `execute`, `insert` (згенерований ID), `execute_many`, `query`, `transaction(read_only=False)`, `health`, `close`. Увесь SQL і списки допустимих динамічних ідентифікаторів належать інтерфейсам `*Db`, а не менеджеру. Значення передавайте через прив’язані параметри драйвера.
- Контекст транзакції комітить лише за успіху й відкочує за винятку, зберігаючи початковий виняток навіть якщо відкат теж завершився помилкою. DDL і створення схеми виконуються окремо від багатокомандних транзакцій даних.
- Предметні класи `*Db` в `interface/` володіють SQL-схемою, індексами, обмеженнями, методами читання/запису, відображенням рядків на сутності й атомарними операціями запису. `activity/` використовує їхні іменовані операції, `entity/` зберігає дані. **Ніколи не імпортуйте GeoIpDb і не створюйте GeoIP-таблиць** у сторонньому застосунку.
- Надавайте невелику внутрішню операцію перевірки стану лише для читання через **налаштоване з’єднання БД застосунку** (наприклад `SELECT 1` через менеджер). Повідомляйте про помилку, коли з’єднання не працює; не приховуйте її, не перепідключайтеся автоматично й не створюйте окреме моніторингове з’єднання. Обробник стану застосунку передає результат CMDB; **CMDB не повинна звертатися до MariaDB безпосередньо для перевірки DB Server**.
- Використовуйте декларації `CMDB_DATABASES` для виявлення застосунку й дотримуйтеся правил BMForge щодо конфігурації та розгортання. Інвентарна декларація не створює користувачів БД, схему чи резервні копії автоматично.
- Явно вибирайте контракт узгодженості й конкурентності записів кожного застосунку. Для служби обліку часу розглядайте ідемпотентні ID подій і транзакційні переходи сесій лише за власними вимогами служби.

## Критерії приймання

1. Підключайтеся до окремої тестової БД із тестовими обліковими даними; відсутні/неправильні дані спричиняють помилку без розкриття паролів.
2. Перевірте запис/читання через прив’язані параметри, включно з Unicode; рядок, схожий на ін’єкцію, зберігається як значення.
3. Кілька записів комітяться атомарно; змодельований збій відкочує всі записи й повторно породжує помилку.
4. Окремі потоки мають окремі власні з’єднання; закриття звільняє ресурси.
5. Некоректна/відсутня конфігурація й недоступність БД дають явні помилки без повідомлення часткового успіху.
6. Внутрішня перевірка БД успішна за працездатного з’єднання, неуспішна при змодельованому збої й робить сукупний `/health` застосунку нездоровим; без прямого підключення CMDB до MariaDB.
7. Присутні лише схема й SQL нового застосунку, без імпортів BMForge/bmgeoip під час виконання. Декларації CMDB відповідають розгортанню.
8. `<app>/interface/DbMgr.py` є незмінною копією `components/templates/db-server/interface/DbMgr.py` з `BMFORGE_COMPONENT` версії `0.4.0`. У менеджері немає прикладного SQL, констант чи назв предметної області.
9. Кожен предметний інтерфейс `*Db` передає SQL і транзакції ін’єктованому `DbMgr`; активності й сутності не звертаються безпосередньо до PyMySQL.
10. DB Server використовує лише схвалені модулі та MariaDB; будь-яка інфраструктурна зміна потребує схвалення користувача перед оновленням специфікації.
