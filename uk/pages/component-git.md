# Git

**Ідентифікатор компонента:** `{{ page.component_id }}` · **Специфікація:** `{{ page.spec_version }}` ({{ page.spec_status }})

Це невеликий інтерфейс, яким **володіє застосунок**, для двох операцій Git: **Publish** і **Commit**. Скопіюйте [локальний шаблон]({{ '/components/templates/git/Git.py' | relative_url }}) у власний пакет застосунку-споживача; не імпортуйте BMForge чи інший застосунок під час виконання. Дотримуйтеся [інженерного контракту]({{ site.baseurl }}{% link uk/pages/engineering-contract.md %}) та [простежуваності компонентів]({{ site.baseurl }}{% link uk/pages/specification-lifecycle.md %}).

## Схвалені модулі виконання

Це повний перелік дозволених модулів цього компонента. Він працює на Linux/POSIX і викликає встановлену **команду Git**; Git є зовнішньою програмою, а не пакетом Python.

| Походження | Модуль | Призначення |
| --- | --- | --- |
| Стандартна бібліотека Python | `contextlib` | Контекстний менеджер для ексклюзивного сеансу публікації |
| Python stdlib / POSIX | `fcntl` | Неблокувальне консультативне блокування окремого репозиторію публікації |
| Стандартна бібліотека Python | `os` | Передавання середовища з `GIT_TERMINAL_PROMPT=0` |
| Стандартна бібліотека Python | `pathlib` | Шляхи репозиторію й керованих файлів |
| Стандартна бібліотека Python | `subprocess` | Запуск установленого Git CLI без оболонки |
| Стандартна бібліотека Python | `tempfile` | Атомарний запис згенерованих файлів публікації |

**Жодних GitPython, Dulwich, ORM, черг завдань або бібліотек GitHub API.** Codex може задавати шляхи, гілку, назви керованих файлів і повідомлення комітів. Якщо цих модулів або підходу через CLI недостатньо, **зупиніться й отримайте схвалення користувача** перед заміною чи додаванням технології. Прикладний код активностей не входить до цього інфраструктурного контракту.

## Операція 1: Commit

`Git(checkout).commit(message)` виконує точно ці команди в обраному **корені репозиторію**:

```sh
git add . -v
git commit -m "<message>"
git push
```

`Git` виконує їх як масиви аргументів із `git -C <checkout>`, а не через оболонку. `push` використовує налаштовану віддалену гілку для поточної гілки; викликач має заздалегідь налаштувати віддалений репозиторій, ідентичність Git і облікові дані для надсилання. Усі зміни в корені репозиторію, включно з невідстежуваними файлами, які Git не ігнорує, переходять у staging.

Після успішного надсилання операція повертає докладний вивід додавання та коміту. Порожнє повідомлення, невідповідність кореня репозиторію, порожній коміт, помилки Git або відхилене надсилання завершуються помітним збоєм. **Невдале надсилання може залишити коміт локально.** Не додавайте автоматичних `pull`, злиттів, повторних спроб, примусового надсилання, очищення або перемикання гілок. Конфлікти розв’язує викликач.

## Операція 2: Publish

`Git(checkout, branch="main", managed_paths=paths).publish(files, message)` публікує відповідність `{relative_path: str_or_bytes}` в **окремому клоні для публікації**, а не в робочому дереві розробника. Використовуйте явний список керованих шляхів, переданий викликачем.

1. Отримайте ексклюзивне неблокувальне блокування в каталозі Git цього клону. Вимагайте правильну гілку, чисте робоче дерево й перебування в корені репозиторію.
2. Виконайте отримання даних із `origin` і швидке переміщення вперед до upstream-комітів. Відмовляйтеся від розбіжної історії чи сторонніх неопублікованих комітів.
3. Записуйте лише дозволені керовані файли, вміст яких змінився. Відхиляйте неузгоджені шляхи й цілі символічних посилань; додавайте й комітьте **лише змінені керовані шляхи**. За відсутності змін нового коміту немає.
4. Надсилайте до `origin` у налаштовану гілку. Повторюйте попереднє невдале надсилання **лише тоді**, коли локальні неопубліковані коміти стосуються керованих файлів; не застосовуйте force-push і не відкидайте коміти мовчки.
5. Повертайте `True`, якщо надсилання успішне, `False`, якщо публікувати нічого; збій має породжувати помилку й не заявляти про успіх.

Застосунок готує дані звіту, вибирає вихідні шляхи та передає повідомлення коміту. Git **не** відображає HTML, не опитує MariaDB, не планує завдання, не створює репозиторії, не налаштовує облікові дані й не виконує злиття чи тегування випусків. Це окремі обов’язки.

## Життєвий цикл і стан

Git — викликаний інтерфейс, **а не запущений сервер**. Він не має слухача чи точки `/health`. Результат `commit` або `publish` повідомляє викликачеві про успішність операції. Власна перевірка стану застосунку може включати можливості Git лише за явної вимоги.

## Критерії приймання

1. Commit додає змінені й невідстежувані файли через `git add . -v`, створює повідомлення та надсилає коміт до налаштованої upstream-гілки.
2. Порожній коміт і відхилене надсилання спричиняють помітний збій; успішний локальний коміт не видаляється через невдале надсилання.
3. Publish змінює лише схвалені керовані файли; незмінний вміст не створює дубльованих комітів.
4. Publish відмовляється працювати з брудним деревом, неправильною гілкою чи одночасною публікацією.
5. Після відхиленого надсилання наступна спроба публікує наявний керований коміт без дублювання.
6. Усі перевірки використовують одноразові локальні репозиторії та bare-remotes; мережеві облікові дані й публічні репозиторії не потрібні.
7. Перевірте, що згенерований застосунок володіє своїм шаблоном Git, декларує буквальні метадані `BMFORGE_COMPONENT` і не імпортує BMForge чи Snake Web під час виконання.
