**У нових проєктах, створених через початкове налаштування Codex, ці файли вже згенеровано:** `scripts/new-release.sh`, перевірку CMDB, константи версії, `CHANGELOG.md` і вимкнені оболонки життєвого циклу розгортання. Не копіюйте їх повторно. Початкове налаштування ніколи не створює коміт і не публікує випуск. Обов’язкова [навичка життєвого циклу встановлення]({{ site.baseurl }}{% link pages/component-installation.md %}) вимагає завершити й перевірити встановлення, оновлення та видалення, включно з успішним маркером установленої версії, перш ніж вважати застосунок готовим до випуску. Самих виконуваних shell-скриптів недостатньо.

Для проєктів, створених вручну, налаштуйте інструменти один раз. Наступні випуски виконуйте за [Створенням випуску]({{ site.baseurl }}{% link uk/pages/creating-a-release.md %}).

## Підготовка констант і журналу змін

Спочатку виконайте [Відповідність CMDB]({{ site.baseurl }}{% link pages/cmdb-compliance.md %}). Визначте канонічну назву застосунку, шлях до констант, буквальний `VERSION` і початковий `CMDB_CODENAME`. Оголосіть постійні компоненти, посилання на бази даних й мережеві слухачі; використовуйте порожні кортежі, якщо їх немає. Для застосунків зі слухачами виконайте [Мережеву конфігурацію]({{ site.baseurl }}{% link uk/pages/network-configuration.md %}), щоб стандартні значення виконання й перевірки життєвого циклу використовували декларацію.

Додайте три точки входу життєвого циклу за [Скриптами встановлення]({{ site.baseurl }}{% link pages/installation-scripts.md %}). Вони повинні бути виконуваними та закоміченими до випуску; розгортання залишається окремою операцією.

Створіть `CHANGELOG.md` із рівно одним заголовком `## [Unreleased]`. [Шаблон журналу змін]({{ '/templates/project/CHANGELOG.md' | relative_url }}) містить початкову структуру. Дотримуйтеся [Ведення журналу змін]({{ site.baseurl }}{% link uk/pages/changelog-maintenance.md %}) під час розробки та обслуговування.

## Установлення скриптів

Для проєктів без початкового налаштування Codex скопіюйте ці файли з BMForge:

| Джерело BMForge | Призначення в проєкті |
| --- | --- |
| [Скрипт випуску]({{ '/templates/project/scripts/new-release.sh' | relative_url }}) | `scripts/new-release.sh` |
| [Перевірка метаданих]({{ '/templates/project/scripts/check-cmdb.py' | relative_url }}) | `scripts/check-cmdb.py` |

Зробіть `scripts/new-release.sh` виконуваним. Потрібні Bash, Git, Python 3.10 або новіший та стандартні утиліти GNU. Проєкти зі статичним PEP 621 `[project].version` у `pyproject.toml` автоматично синхронізують версію; спочатку вона має збігатися з буквальним `VERSION` застосунку. Скрипт читає та змінює метадані без імпорту коду застосунку.

Замініть `__PROJECT_NAME__` і `__PROJECT_SLUG__` у блоці параметрів скрипту канонічною назвою застосунку та її формою в нижньому регістрі. Перевірте шлях версії, шлях журналу змін, віддалений репозиторій і назви гілок. Стандартні значення: `origin`, `dev`, `main` і `feat/maint-`.

Відстеження впливу розгортання налаштовується окремо. Залиште `dependency_rules` і `deployment_config` порожніми, доки не буде готове [Відстеження впливу розгортання]({{ site.baseurl }}{% link pages/deployment-impact-tracking.md %}); використовуючи його, увімкніть обидва параметри разом.

## Створення гілок

Для проєктів, створених через **початкове налаштування Codex**, локальний менеджер створює початкові *локальні* гілки випусків після переглянутого користувачем коміту на `main`:

```sh
python3 .agents/bmforge/manage.py setup-branches --project . --dry-run
python3 .agents/bmforge/manage.py setup-branches --project .
```

Перша команда перевіряє передумови без зміни Git-посилань. Друга створює `dev` і `feat/maint-0.1.0` на основі початкового коміту `main` і переходить у функціональну гілку. Вона **не** створює коміт, не публікує гілку в `origin`, не налаштовує віддалений репозиторій і не створює випуск. Спочатку перегляньте та закомітьте створену структуру. Не створюйте повторно й не перезаписуйте наявні гілки; узгоджуйте віддалені посилання `dev` і функціональних гілок окремо.

Для проєктів **без** початкового налаштування Codex скористайтеся початковими ручними командами.

Почніть із закоміченого проєкту на `main` і налаштованого `origin`. Створіть гілку розробки й першу функціональну гілку:

```sh
git switch main
git switch -c dev
git switch -c feat/maint-0.1.0
```

Якщо `dev` уже існує, використовуйте її. Функціональні гілки походять від `dev`. Перед кожним випуском `main` має бути предком `dev`, а `dev` — предком функціональної гілки. Локальні `main` і `dev` мають містити зміни відповідних віддалених гілок. Скрипт може створити відсутні віддалені гілки під час надсилання випуску.

## Перевірка налаштування

- Запустіть перевірку метаданих зі справжньою назвою проєкту й шляхом констант.
- Запустіть `bash -n scripts/new-release.sh` і `scripts/new-release.sh --help`.
- Закомітьте скрипти, константи, журнал змін і налаштовані метадані розгортання до випуску.
- Перевірте адаптований скрипт випуску в одноразовому репозиторії з локальним bare remote. Перевірте відповідність версії, кодової назви, журналу змін, вершин гілок й анотованого тега.
