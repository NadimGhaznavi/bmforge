Забезпечуйте застосункам передбачуваний конфігураційний файл, щоб оператори могли змінювати розгортання без редагування вихідного коду, а CMDB могла виявляти його робочі налаштування. Використовуйте однакові стандартні значення та правила перевизначення під час запуску застосунку, в операційних інструментах і виявленні.

## Визначення конфігураційного контракту

Зберігайте налаштування конкретного розгортання в `/opt/prod/<lowercase-name>/conf/<lowercase-name>.json`, використовуючи канонічну назву з [Відповідності CMDB]({{ site.baseurl }}{% link pages/cmdb-compliance.md %}). Визначайте шлях від кореня встановленого застосунку незалежно від робочого каталогу викликача. Константа `CONFIG_FILE` може містити відносний шлях, наприклад `conf/bmgeoip.json`.

Зберігайте стандартні значення випуску у файлі констант, а перевизначення оператора — в JSON. Зміна налаштувань одного розгортання не повинна вимагати редагування констант або нового випуску. Метадані випуску, зокрема `VERSION` і `CMDB_CODENAME`, залишаються в константах і не належать до конфігурації виконання.

Документуйте кожен параметр: його JSON-ключ, тип, стандартну константу, правила перевірки та момент набрання чинності. Групуйте пов’язані параметри в іменованих об’єктах, наприклад `network`. Використовуйте стабільні ключі, щоб оператори, інструменти й CMDB трактували їх однаково.

## Стандартні значення та перевизначення

Застосовуйте пріоритет від найнижчого до найвищого:

1. Стандартні значення з файла констант.
2. Перевизначення з робочого JSON.
3. Підтримувані аргументи командного рядка конкретного запуску.

За відсутності файла застосовуються стандартні значення. Частковий файл перевизначає тільки вказані параметри; пропущені групи й поля успадковують стандартні значення. Явно записане значення є перевизначенням, навіть якщо збігається з поточним стандартним. Воно залишиться фіксованим після зміни стандартного значення в новому випуску. Пояснюйте цю різницю при створенні повного початкового файла: заповнені значення стають налаштуваннями розгортання, а пропущені слідують за майбутніми стандартними значеннями.

Реалізуйте один спільний конфігураційний інтерфейс для читання, перевірки й визначення значень. Споживачі повинні використовувати його, а не дублювати резервні значення чи читати JSON незалежно. Застосовуйте ті самі правила до запуску служб, працівників, згенерованих конфігурацій служб, інструментів перезапуску й перевірок працездатності, коли це застосовно.

Відхиляйте некоректний JSON, невідомі ключі, неправильні типи й недійсні значення. Називайте файл і параметр у повідомленні про помилку. Лише відсутній файл дозволяє повернення до стандартних значень; нечитабельний чи неправильний файл має спричиняти явний збій. Перевіряйте файл, навіть якщо аргументи поточного запуску перекривають проблемні параметри.

## Приклад: слухачі BMGeoIP

BMGeoIP визначає стандартні слухачі в `bmgeoip/constants/DBMGeoIP.py`:

```python
CMDB_NETWORK = (
    ("http", "0.0.0.0", 54300),
    ("zmq", "0.0.0.0", 54301),
)
CONFIG_FILE = "conf/bmgeoip.json"
```

Оператор може створити `/opt/prod/bmgeoip/conf/bmgeoip.json`:

```json
{
  "network": {
    "http": {"interface": "127.0.0.1", "port": 54310},
    "zmq": {"interface": "127.0.0.1"}
  }
}
```

Визначена HTTP-прив’язка — `127.0.0.1:54310`. Прив’язка ZMQ — `127.0.0.1:54301`, її порт успадковується з констант. Без файла обидва слухачі використовують оголошені стандартні значення. Підтримуваний аргумент HTTP-порту перекриває `54310` для одного запуску без змін обох файлів.

Дивіться [Мережеву конфігурацію]({{ site.baseurl }}{% link uk/pages/network-configuration.md %}) щодо декларацій слухачів, перевірки адрес і портів, прив’язок і клієнтських адрес призначення. Інші конфігуровані функції дотримуються такого самого співвідношення констант і JSON із власною задокументованою схемою.

## Доступність налаштувань для виявлення

Забезпечте обліковому запису інвентаризації CMDB читання встановлених констант і несекретного JSON, включно з доступом до каталогів. JSON є даними: для визначення перевизначень CMDB не повинна імпортувати модулі застосунку, виконувати його код чи завантажувати shell-файли.

Контракт виявлення поєднує стандартні значення випуску з JSON-перевизначеннями за тією самою схемою й пріоритетом, що й застосунок. Константи описують стандартні значення випуску, а JSON — вибір розгортання. Жоден із цих файлів окремо не обов’язково описує фактичні налаштування. При додаванні або перейменуванні параметрів явно зберігайте відповідність.

Аргументи командного рядка діють на окремий запуск. Документуйте підтримувані перевизначення й те, як вони видимі системі виявлення, щоб відрізняти постійні налаштування від параметрів процесу. Для тривалих змін використовуйте JSON.

Облікові дані й секрети зберігайте в окремих захищених файлах або механізмі керування секретами проєкту. Наприклад, BMGeoIP зберігає дані входу до БД в `/etc/bmgeoip/database.env`. JSON для виявлення не повинен вимагати доступу до секретів.

## Збереження конфігурації під час розгортання

Інтегруйте конфігурацію зі [Скриптами встановлення]({{ site.baseurl }}{% link pages/installation-scripts.md %}):

- Під час першого встановлення створюйте робочий JSON лише якщо його немає, використовуючи стандартні значення з констант, а не другу жорстко задану копію.
- Зберігайте наявні файли при перевстановленні й оновленні. Перевіряйте їх на відповідність новому випуску перед зупинкою служб. Зміни схеми виконуйте через явні міграції зі збереженням вибору оператора.
- Тримайте робочий JSON поза копійованими артефактами вихідного коду й очищенням керованих файлів. Під час видалення залишайте його згідно зі стандартним контрактом життєвого циклу, якщо проєкт не визначає іншу політику.
- Визначайте параметри один раз на процес і документуйте, що після редагування потрібен перезапуск. Надавайте точку перезапуску, яка перевіряє конфігурацію перед застосуванням змін до всіх відповідних служб і згенерованих конфігурацій.
- Виконуйте перевірки стану з тими самими фактичними параметрами, що й застосунок. За наявності [Відстеження впливу розгортання]({{ site.baseurl }}{% link pages/deployment-impact-tracking.md %}) включайте конфігураційний код, стандартні значення й операційних споживачів.

Стартовий інсталятор не містить резолвера конфігурації застосунку й не керує цим JSON. Реалізуйте життєвий цикл конфігурації до ввімкнення `DEPLOYMENT_READY`.

## Перевірка контракту

Перевірте відсутні й часткові файли, явні перевизначення, пріоритет аргументів запуску й зміну стандартних значень випуску. Переконайтеся, що некоректна, нечитабельна й недійсна конфігурація спричиняє збій до змін служб. Підтвердьте, що застосунок та операційні інструменти визначають ті самі значення.

Перевірте збереження потрібних налаштувань під час першого встановлення, перевстановлення, оновлення й видалення. Після редагування JSON і перезапуску перевірте фактичну поведінку застосунку та відповідні параметри розгортання у CMDB. Оновлюйте приклади та відповідність параметрів константам зі змінами схеми.
