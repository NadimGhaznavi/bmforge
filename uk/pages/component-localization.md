# Локалізація застосунків

**Ідентифікатор компонента:** `{{ page.component_id }}` · **Специфікація:** `{{ page.spec_version }}` ({{ page.spec_status }})

## Призначення

Готуйте **багатомовні інтерфейси застосунків від першого випуску**, не припускаючи, що якусь додаткову мову вже перекладено. Це **не переклад документації Jekyll**: [Багатомовна документація]({{ site.baseurl }}{% link uk/pages/multilingual-documentation.md %}) навмисно відкладає повні переклади до стабілізації вмісту. Натомість інтерфейс застосунку, CLI та повідомлення для людей використовують стабільні ключі локалізації від початку.

Наявний форк Minimal Mistakes є еталоном виявлення мови, ручного вибору й резервної мови; блог — еталоном перекладеного вмісту й підписів таксономії, які змінюються лише на екрані. Реалізація застосунку — невеликий **локалізатор стандартної бібліотеки Python**, а не перенесення Liquid, Jekyll, браузерних перенаправлень чи ресурсів теми.

## Схвалені модулі виконання

| Походження | Модуль | Дозволене використання |
| --- | --- | --- |
| Стандартна бібліотека Python | `json` | Завантаження UTF-8 каталогів повідомлень, якими володіє застосунок |
| Стандартна бібліотека Python | `pathlib` | Пошук файлів каталогів у пакеті |
| Стандартна бібліотека Python | `re` | Перевірка тегів локалі й простих назв полів-підстановок |
| Стандартна бібліотека Python | `string` | `Formatter` для перевірки іменованих підстановок |
| Стандартна бібліотека Python | `enum` | `StrEnum` для стабільних ключів повідомлень `DText` (окремий модуль констант) |

Додаткових pip-залежностей не потрібно. Якщо застосунок використовує HTTP Display Server, його схвалений Jinja2-рендерер забезпечує екранування; `jinja2` **не** є додатковою залежністю локалізатора. **Не додавайте непомітно Babel, розширення gettext, служби машинного перекладу, брокери локалей, фронтенд-фреймворки чи бази перекладів.** Для можливостей поза невеликим контрактом, наприклад граматичних форм множини чи локального форматування дат і чисел, отримайте схвалення користувача та оновіть специфікацію.

## Канонічні файли й відповідальність застосунку

Скопіюйте `components/templates/localization/interface/Localizer.py` **без змін** до `<app>/interface/Localizer.py`. Він містить буквальний маркер `BMFORGE_COMPONENT` для `bmforge.localization` версії `0.1.0`. Скопіюйте `components/templates/constants/DText.py` до `<app>/constants/DText.py` і **адаптуйте список ключів** до реальних повідомлень. Скопіюйте `components/templates/localization/locales/en.json` до `<app>/locales/en.json`, замінивши приклади на відповідний англомовний текст.

```text
<app>/
  constants/DText.py           stable keys: app.title, timer.start, ...
  interface/Localizer.py       identical standard-library localizer
  locales/en.json              complete source-language catalogue
  locales/fr.json              optional real translations, when approved
```

Активності й презентаційні компоненти звертаються до `localizer.text(DText.APP_TITLE, locale=language)`, а **не** містять жорстко задані підписи `"Start timer"` або `"Running"`. `DStatus.RUNNING`, збережені значення, назви API-методів, ключі полів JSON, SQL-стовпці, **коди** помилок, URL і команди залишаються канонічними й неперекладеними. Це та сама відмінність, яку блог використовує між локалізованими *підписами* тегів та їх канонічними ID.

## Узгодження локалі й резервна мова

- Англійська (`en`) обов’язкова та містить повний набір ключів повідомлень. Інші каталоги — UTF-8 JSON зі стабільними ключами й текстом для людей; часткові переклади дозволені з **резервним англійським текстом для кожного ключа**.
- У браузерному запиті **явний вибір користувача** (наприклад `?lang=fr`) переважає список уподобань `Accept-Language`. Без явного вибору розбирайте впорядковані мовні теги та допустимі `q`-значення й вибирайте першу підтримувану відповідність. Непідтримувані вподобання повертаються до `en`.
- Для порівняння нормалізуйте регістр і підкреслення; спочатку точна локаль, потім **лише явні батьківські локалі** (`fr-CA` → `fr`; `zh-Hant-HK` → `zh-Hant` → `zh`). **Ніколи не підмінюйте сусідні локалі** на кшталт `zh-TW` замість `zh-CN`.
- Вибір користувача належить до конкретного запиту, а не до глобального стану процесу. Застосунок може явно зберігати мовне вподобання лише за відповідною вимогою; базовий локалізатор не створює cookies, local storage чи автоматичних перенаправлень. Видимий перемикач з’являється лише коли справді є кілька перекладених мов, а не в англомовному застосунку.
- Передавайте вибрану мову крізь навігацію UI (наприклад параметрами запитів) і встановлюйте HTML-атрибут `lang`. Використовуйте безпечні DOM API чи екранування HTML Jinja2. Не трактуйте переклади або підстановки користувача як довірений HTML.

Для CLI визначайте мову з аргументу користувача чи відповідного середовища та використовуйте той самий каталог. Структуровані/API/журнальні ідентифікатори залишайте незмінними, щоб моніторинг і споживачі не залежали від перекладеного тексту.

## Цілісність перекладів

- Ключі `DText` і англійський JSON мають збігатися; для нового тексту інтерфейсу потрібен стабільний ключ до відображення. Відсутній англійський ключ — помилка, а не підстава вигадати підпис.
- Перекладені файли можуть бути неповними, але **не можуть містити невідомих ключів**. Іменовані підстановки, як `{name}`, повинні мати той самий набір імен, що й англійський текст. Вирази атрибутів/індексів чи виконання форматних кодів не підтримуються.
- Локалізатор не виконує автоматичного перекладу. Додавайте лише переклади, надані користувачем або свідомо замовлені й перевірені; не оголошуйте англомовний застосунок багатомовним без справжнього перекладу.
- Код не містить граматики множини, локального форматування чисел/календаря чи рушія RTL-розмітки. Якщо це потрібно, визначте поведінку й отримайте схвалення нової специфікації замість удавати, що пошук рядка вирішує всю інтернаціоналізацію.

## Критерії приймання

1. Англомовний застосунок показує всі повідомлення для людей через стабільні ключі `DText` і вихідний каталог без нової pip-залежності.
2. Другий каталог додається без зміни локалізатора; перекладені значення відображаються, а відсутні повертаються до англійської.
3. Явний вибір переважає браузерні вподобання; порядок якості `Accept-Language`, резервна батьківська мова, неправильні заголовки й відсутні вподобання обробляються передбачувано.
4. Сусідні локалі за системою письма/регіоном не змішуються; `zh-CN` не підмінюється на `zh-TW`.
5. Відсутні вихідні ключі, невідомі ключі перекладу, небезпечні підстановки та невідповідність множин підстановок спричиняють явну помилку.
6. Паралельні HTTP-запити/CLI-операції можуть працювати різними мовами без зміни глобальної локалі; людські підписи перекладаються, а мережеві, статусні й DB-значення залишаються стабільними.
7. HTML безпечно екранується, перемикач мов враховує реально опубліковані локалі, а UI вказує вибраний `lang`. Не робіть висновків про браузерне відображення лише з HTTP-перевірки стану.
