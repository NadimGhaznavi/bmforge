# Activity / Interface / Entity

BMForge використовує класифікацію **Activity / Interface / Entity**, натхненну *Unified Software Development Process* (USDP). Вона розділяє відповідальність керування, меж взаємодії та сутностей, зберігаючи назви й домовленості наявних застосунків. Мета — зрозуміла структура, а не фреймворк.

**Класифікуйте кожен суттєвий клас застосунку за його відповідальністю**, а потім розміщуйте у відповідному пакеті самого застосунку:

| Класифікація | Розташування | Відповідальність | Приклад |
| --- | --- | --- | --- |
| **Activity** | `<app>/activity/` | Координує сценарій використання, перетворює дані й ухвалює рішення застосунку | `CollectVisit`, `PublishStatus` |
| **Interface** | `<app>/interface/` | Взаємодіє із зовнішньою системою **або абстрагує таку взаємодію в термінах предметної області** | `DbMgr`, `VisitorDb`, `MiningDb`, видавець Git, клієнт GeoIP |
| **Entity** | `<app>/entity/` | Зберігає предметні дані та результати без відповідальності за збереження чи передавання | `Visit`, `ExperimentStatus` |

Класифікація визначається **відповідальністю**, а не просто наявністю методів у Python-класі. Це не абстрактні базові класи Python. Вони не потребують успадкування, автоматичної реєстрації, контейнера чи ORM.

## Потік даних і межі залежностей

Для операції з базою даних:

```text
HTTP / ZeroMQ / CLI boundary
          |
          v
  activity/CollectVisit.py          operates on entity/Visit.py
          |
          v
  interface/VisitorDb.py            named domain operations and SQL
          |
          v
  interface/DbMgr.py                connection, cursor, transaction
          |
          v
         MariaDB
```

- **Activities** координують предметні операції та викликають **іменовані методи** інтерфейсів. Вони не створюють курсори, не виконують SQL і не виконують роль контейнерів даних.
- **Предметні інтерфейси**, наприклад `VisitorDb` або `MiningDb`, відповідають за назви таблиць, SQL, параметри запитів, відображення даних і межі транзакцій своєї предметної області. Вони отримують загальний `DbMgr` **через композицію**. Створюйте стільки спеціалізованих предметних інтерфейсів, скільки потрібно, використовуючи той самий загальний менеджер.
- **Технічні інтерфейси**, наприклад `DbMgr`, відповідають за механіку драйвера. Вони **нічого не знають** про відвідування, майнінг, симуляції чи схему застосунку.
- **Сутності** зберігають значення, які передаються між активностями й інтерфейсами. Вони не відкривають з’єднань із базою даних, не виконують SQL, не публікують файлів і не викликають віддалених служб.

У застосунку можуть залишатися пакети `server/`, `zmq/`, `constants/` і `scripts/` для своїх завдань. Не переміщуйте точки входу транспортного рівня довільно лише для дотримання правила каталогів. Класифікуйте класи за **фактичною відповідальністю**; тримайте один суттєвий клас у модулі з невеликими локальними допоміжними функціями за потреби.

## Застосування класифікації

Для нового сценарію визначте сутності й активність, виберіть необхідні технічні інтерфейси та створіть предметний інтерфейс лише там, де це виправдано збереженням даних або іншою межею застосунку. Активність звертається до `VisitorDb.record(visit)`, а не до `DbMgr.execute(...)`. `VisitorDb` викликає `DbMgr` і не має відкривати власне з’єднання PyMySQL.

Для спільних шаблонів скопіюйте відповідний **шаблон BMForge** до цільового застосунку. Не імпортуйте модулі виконання з інших проєктів. Не копіюйте предметну логіку еталонного застосунку. Визначайте спеціалізовані назви, константи й SQL поза загальним компонентом.

### Закріплені приклади

Наведені **незмінні** файли MyCount, скопійовані з коміту `90574cd838ba43499a825c6a193b43cbc485c91c`, демонструють ролі:

| Приклад | Класифікація | Причина |
| --- | --- | --- |
| `components/reference/mycount/mycount/activity/CollectVisit.py` | Activity | Координує підготовку, збагачення та збереження |
| `components/reference/mycount/mycount/interface/VisitDb.py` | Interface, предметний DAL | Містить SQL відвідувань і викликає переданий `DbMgr` |
| `components/reference/mycount/mycount/entity/Visit.py` | Entity | Зберігає дані, що переміщуються між рівнями |

Ці файли мають імпорти, специфічні для MyCount, і **не є готовими загальними модулями**. Поточний канонічний шаблон бази даних — `components/templates/db-server/interface/DbMgr.py`, описаний у [DB Server]({{ site.baseurl }}{% link pages/component-db-server.md %}). Знімки показують межі відповідальності, а не вимогу копіювати MyCount.

## Критерії приймання Codex

1. Визначайте та зберігайте класифікацію відповідальності для нових і змінених суттєвих класів.
2. Розміщуйте координацію предметних операцій у `activity/`, мости між предметною областю й технологіями в `interface/`, а предметні дані в `entity/`. Не створюйте порожніх пакетів для невикористаних ролей.
3. Використовуйте звичайні конструктори й композицію для передавання залежностей. Не вигадуйте ієрархію базових класів або фреймворк ін’єкції залежностей.
4. Предметні класи бази даних використовують лише вибраний `DbMgr` для виконання SQL і транзакцій. Класи Activity/Entity не імпортують `pymysql`.
5. Тримайте метадані походження CMDB `BMFORGE_COMPONENT` **окремо** від класифікації ролей класів. Остання визначається відповідальністю й пакетом у вихідному коді; окремий класифікатор під час виконання не потрібен.
