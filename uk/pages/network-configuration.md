Використовуйте `CMDB_NETWORK` як єдине джерело стандартних налаштувань мережевих слухачів застосунку. Дотримуйтеся спільного контракту [Конфігурації виконання]({{ site.baseurl }}{% link uk/pages/runtime-configuration.md %}) для констант, робочого JSON, виявлення та життєвого циклу розгортання. Цей посібник визначає мережеву схему та її споживачів.

## Оголошення стандартних значень

Розміщуйте безпосередній буквальний запис у наявному файлі констант згідно з [Відповідністю CMDB]({{ site.baseurl }}{% link uk/pages/cmdb-compliance.md %}). Для умовного застосунку Example:

```python
CMDB_NETWORK = (
    ("http", "0.0.0.0", 18080),
    ("backend", "127.0.0.1", 18081),
)
```

Кожен запис — буквальний кортеж `(use, interface, port)`. `use` — унікальна непорожня назва ролі, стабільна для конфігурації й споживачів; без пробілів на краях. `interface` — рядок адреси IPv4. `port` — ціле число від 1 до 65535; булеві та рядкові значення неприпустимі. Анотовані присвоєння підтримуються. Якщо слухачів немає, використовуйте `CMDB_NETWORK = ()`.

Оголошуйте всі слухачі, якими володіє чи які налаштовує застосунок, включно з внутрішніми службами та керованими проксі. Вихідні з’єднання з базами даних та іншими залежностями налаштовуйте окремо; посилання на бази даних належать до `CMDB_DATABASES`. Не включайте облікові дані до декларації та мережевого JSON. Імена хостів, IPv6, Unix-сокети та транспортні розширення не входять до поточного шаблону; `use` позначає роль без окремого поля транспорту.

## Визначення налаштувань виконання

Реалізуйте спільний конфігураційний інтерфейс і мережевий резолвер за шаблоном `Configuration` і `Network` з CMDB та MyCount. Отримуйте значення за роллю, наприклад `Network.binding("http")`, з поверненням `(interface, port)`. Приберіть звернення до позицій кортежів, дубльовані резервні значення та старі константи слухачів. Самого копіювання декларації констант недостатньо для підключення слухачів застосунку.

Пропускайте через цей резолвер запуск сервера, слухачі й upstream-адреси керованих проксі, перевірки працездатності під час встановлення, створення й очищення налаштувань маршрутизатора, якщо такі споживачі є. Локальні клієнти використовують `Network.destination(use)`: вона замінює адресу прив’язування `0.0.0.0` на `127.0.0.1`, залишаючи конкретні адреси незмінними.

Пріоритет від найнижчого до найвищого:

1. Буквальні стандартні значення `CMDB_NETWORK`.
2. Робочі перевизначення JSON у `/opt/prod/<lowercase-name>/conf/<lowercase-name>.json`.
3. Підтримувані перевизначення командного рядка для поточного виклику.

Часткова конфігурація Example:

```json
{
  "network": {
    "http": {
      "interface": "127.0.0.1",
      "port": 19080
    }
  }
}
```

Якщо файл відсутній, діють стандартні значення. Пропущені ролі й поля успадковують стандартні значення. Відхиляйте некоректний JSON, невідомі ролі чи поля, недійсні IPv4-адреси та порти з помилкою, що називає файл або параметр. Некоректна конфігурація має спричиняти збій, а не непомітне повернення до стандартних значень. Обчислюйте конфігурацію один раз на процес і перезапускайте відповідні процеси після редагування. Зберігайте наявні підтримувані перевизначення CLI.

Декларація описує стандартний інвентар. Робочий JSON і CLI можуть змінювати фактичну прив’язку без зміни декларації. Дотримуйтеся контракту виявлення конфігурації виконання, щоб CMDB і споживачі однаково тлумачили стандартні значення та перевизначення.

## Інтеграція зі встановленням і перезапуском

Розширте [Скрипти встановлення]({{ site.baseurl }}{% link uk/pages/installation-scripts.md %}), щоб створювати доступний для читання робочий JSON із декларації лише за відсутності файла. Зберігайте наявну конфігурацію під час перевстановлення й оновлення. Перевіряйте її перед зупинкою служб. Під час видалення залишайте поточну конфігурацію за контрактом життєвого циклу BMForge, якщо проєкт явно не описує іншу політику.

Для застосунків зі службами створіть точку перезапуску. Спочатку перевіряйте конфігурацію, потім застосовуйте всі відповідні налаштування, включно зі згенерованою конфігурацією проксі чи правилами маршрутизатора. Перевірки працездатності мають використовувати ті самі визначені параметри, що й служби. Завершіть і перевірте цю спеціалізовану роботу до ввімкнення `DEPLOYMENT_READY` у стартовому інсталяторі; стартовий інсталятор не містить резолвера виконання та не керує мережевим JSON.

Включайте резолвер, стандартні конфігурації, інструменти перезапуску, шаблони проксі й пов’язані перевірки стану у [Відстеження впливу розгортання]({{ site.baseurl }}{% link uk/pages/deployment-impact-tracking.md %}), якщо його ввімкнено.

## Перевірка застосунку

- Запустіть перевірку метаданих, щоб підтвердити буквальну декларацію. Для наявних проєктів її відсутність допускається; якщо вона є, її перевіряють.
- Змініть стандартні значення в тесті й переконайтеся, що сервер, проксі, перевірки стану та маршрутизатор використовують нові прив’язки там, де це застосовно.
- Перевірте відсутній і частковий JSON та пріоритет CLI.
- Перевірте, що некоректний JSON, невідомі параметри, адреси й порти спричиняють збій до зупинки служб чи перезапуску.
- Переконайтеся, що перевстановлення й оновлення зберігають робочу конфігурацію, а перезапуск застосовує зміни до всіх потрібних компонентів.
- Приберіть замінені константи та жорстко задані стандартні адреси слухачів. Після розгортання перевіряйте фактичні прив’язки й стан окремо від виявлення CMDB.
