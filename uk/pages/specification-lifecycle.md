# Життєвий цикл специфікацій і простежуваність

BMForge визначає **поточні рекомендовані контракти** для нових реалізацій. Кожен застосунок володіє власною реалізацією та може свідомо оновлювати її без залежності від BMForge під час виконання.

## Визначення реалізованого контракту

Кожен компонент, створений на основі BMForge, має містити один буквальний маркер у **власному Python-модулі**, наприклад сервер ZeroMQ у DevLog:

```python
BMFORGE_COMPONENT = {
    "id": "bmforge.zmq-server",
    "spec_version": "0.3.0",
}
```

Стабільний ідентифікатор визначає компонент BMForge, а версія — специфікацію, за якою реалізацію створено або перевірено. Це **не** версія випуску застосунку. Маркер розміщують у модулі-власнику компонента, а не в кожному допоміжному файлі. Оголошення має містити буквальні рядки, щоб у майбутньому його можна було розібрати статично через Python AST, не імпортуючи й не виконуючи код застосунку. Імпорт BMForge під час виконання не потрібен.

Маркер є **твердженням про походження**, а не доказом відповідності. Відповідність реалізації контракту підтверджують тести. Походження компонента не залежить від [класифікації класів, натхненної USDP]({{ site.baseurl }}{% link pages/classification.md %}), яка визначається відповідальністю класів і розташуванням у пакетах; додаткова система метаданих під час виконання не потрібна. Список схвалених модулів виконання кожного компонента є частиною версійної специфікації; зміна інфраструктурних модулів потребує схвалення користувача й нової версії специфікації.

## Розвиток специфікації

1. Дослідіть збій у застосунку-споживачі. Відрізніть дефект реалізації від відсутньої чи помилкової вимоги BMForge.
2. Якщо виявлено прогалину специфікації, уточніть поведінку й додайте цільову приймальну або регресійну перевірку.
3. Змініть версію специфікації, коли змінюються її обов’язкові вимоги. Не використовуйте опубліковану версію повторно для іншого контракту. Зберігайте опубліковані версії як незмінні ревізії Git або знімки, щоб старі маркери залишалися змістовними.
4. Оновіть поточну сторінку специфікації, приймальні перевірки та [журнал рішень]({{ site.baseurl }}{% link DECISIONS.md %}), якщо зміна впливає на інженерну політику чи сумісність.
5. Споживачі свідомо приймають нову версію, перевіряють її локально та оновлюють власні маркери модулів.

Метадані сторінки кожного компонента визначають стабільний `component_id`, `spec_version` і `spec_status`. HTTP і ZeroMQ мають статус **чернетки 0.3.0**, а канонічний MariaDB DB Server і контракт шарів DAL — **чернетки 0.4.0**; усі очікують перевірки у застосунках-споживачах. Специфікація Git має незалежне версіонування. Не змішуйте версії специфікацій із версіями випусків застосунків.

## Межа CMDB і майбутня видимість

Майбутній сканер коду CMDB зможе отримувати маркери `BMFORGE_COMPONENT` і порівнювати версії встановлених компонентів із каталогом BMForge. Це забезпечить запити як від застосунку до специфікації, так і від специфікації до застосунків.

**Цього сканера й порівняльного звіту поки немає.** Наявне оголошення `CMDB_COMPONENTS` інвентаризує постійні каталоги для резервного копіювання й виявлення; його не можна перепризначати для позначення архітектурних компонентів BMForge.

Реалізація, створена до останньої специфікації, не обов’язково є вразливою чи дефектною. Актуальність версії, перевірена відповідність і відомі ризики безпеки — окремі факти.
