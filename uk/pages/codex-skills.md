# Навички компонентів Codex

**Глобальна навичка початкового налаштування** BMForge встановлює **локальні для проєкту закріплені навички компонентів** у новий Git-репозиторій. Codex виявляє лише навички в цільовому проєкті, а не весь репозиторій BMForge. Кожна навичка містить чинний контракт та вибраний еталонний код. Бізнес-логіка застосунку й запущена служба не генеруються. Початкове налаштування створює закріплені навички й установлену структуру інструментів випуску.

## Одноразове встановлення початкової навички

У Codex використовуйте вбудований інсталятор навичок:

```text
$skill-installer install https://github.com/NadimGhaznavi/bmforge/tree/main/skills/bmforge-new-project
```

Або з робочої копії BMForge:

```sh
mkdir -p ~/.agents/skills
cp -R skills/bmforge-new-project ~/.agents/skills/
```

Ця **глобальна** навичка міститься в `~/.agents/skills/bmforge-new-project/`. Використовуйте `$bmforge-new-project` у цільовому Git-репозиторії. Навичка запитує, які компоненти потрібні новому застосунку, не припускаючи конкретної програми чи технології.

## Приклад нового проєкту

Якщо Git уже ініціалізовано в цільовому репозиторії, схвалений користувачем вибір HTTP і MariaDB можна встановити так:

```sh
python3 ~/.agents/skills/bmforge-new-project/scripts/manage.py init \
    --project /path/to/new-repository \
    --name AcmeApp \
    --components bmforge-http,bmforge-db-server
```

**Не** сприймайте назву або вибір компонентів із прикладу як стандартні значення. Обов’язковий `--name` — назва Python-класу (наприклад `SnakeLab`), а не вгадана назва репозиторію; необов’язковий `--subtype` задає підтип CMDB, стандартно `Application`. Без `--components` встановлюються чотири **базові стандарти**: `bmforge-project`, `bmforge-constants`, `bmforge-localization` та `bmforge-installation`. Вони додають інструкції, приклади англомовного каталогу повідомлень і закріплені шаблони, але не генерують код застосунку. Наявні `AGENTS.md` або файли `.agents/` ніколи не перезаписуються.

Структура нового репозиторію:

```text
AGENTS.md
CHANGELOG.md
acmeapp/
  constants/DAcmeApp.py
scripts/
  new-release.sh       # executable
  check-cmdb.py
  install.py           # deployment disabled
  install.sh           # executable
  upgrade.sh           # executable
  uninstall.sh         # executable
.agents/
  bmforge/
    manage.py
    lock.json
  skills/
    bmforge-project/
      SKILL.md
      references/
    bmforge-constants/
      SKILL.md
      assets/DProject.py
    bmforge-localization/
      SKILL.md
      assets/Localizer.py
      assets/DText.py
      assets/en.json
    bmforge-installation/
      SKILL.md
      references/specification.md
      references/source/devlog/
    bmforge-http/
      SKILL.md
      references/
    bmforge-db-server/
      SKILL.md
      references/
      assets/DbMgr.py
```

Коміт вихідного коду кожного встановленого компонента, версія специфікації та відбиток вмісту записуються в `lock.json`. Початкові шаблони випуску входять до закріпленої навички `bmforge-project`, тому зміни в BMForge **лише повідомляються як доступні**, а не застосовуються до файлів випуску проєкту. Компоненти доступні локально, навіть якщо BMForge пізніше недоступний. **Жодних імпортів BMForge під час виконання**; установлення навичок не створює портів, баз даних, функцій застосунку або служб. Файли випуску готуються, **але не виконуються**. Після створення застосунку базова [навичка життєвого циклу встановлення]({{ site.baseurl }}{% link uk/pages/component-installation.md %}) вимагає завершити й протестувати всі три операції до першого випуску. Кожне успішне встановлення записує версію у власному каталозі `/opt/prod`, навіть для власної бібліотеки або CLI. Налаштуйте розгортання, Git origin та гілки main/dev/feature і закомітьте проєкт перед випуском. Дивіться [Налаштування випусків]({{ site.baseurl }}{% link uk/pages/release-setup.md %}).

## Доступні навички

| Локальна навичка проєкту | Призначення |
| --- | --- |
| `bmforge-project` | Інженерна політика й класифікація Activity / Interface / Entity (завжди) |
| `bmforge-constants` | Типізовані константи за предметними областями та стабільні машинні ідентифікатори (завжди) |
| `bmforge-localization` | Вибір локалі для запиту й англійський вихідний каталог (завжди) |
| `bmforge-installation` | Завершення встановлення/оновлення/видалення, версійна ідентичність у `/opt/prod` й необов’язкові ролі клієнта/сервера (завжди) |
| `bmforge-http` | HTTP-сервер на стандартній бібліотеці й необов’язковий Jinja2 |
| `bmforge-zmq` | Сервер PyZMQ REQ/REP і контракт обробки повідомлень |
| `bmforge-db-server` | Незмінний канонічний MariaDB `DbMgr.py` та предметні інтерфейси `*Db` |
| `bmforge-git` | Коміт усіх змін і push або публікація керованих файлів |
| `bmforge-visualization` | Графіки Plotly.js, карти Leaflet, графи топології Cytoscape.js |
| `bmforge-gif-animation` | Кодування GIF-кадрів Pillow з керованими тривалостями, палітрами, повторенням і байтовим/файловим результатом |

**Наявні проєкти:** оновлення глобальної навички початкового налаштування чи закріплених локальних навичок усе одно потребує явного перегляду та схвалення. Перевірка лише читання повідомляє про доступні зміни менеджера й наборів навичок; вона не встановлює новий базовий набір заднім числом у раніше створених проєктах. Нове початкове налаштування відразу містить оновлений базовий набір.

Пізніше можна явно додати необов’язковий компонент:

```sh
python3 .agents/bmforge/manage.py add --project . --components bmforge-zmq
```

Операція `add` відмовляється перезаписувати встановлену навичку.

## Створення стандартних гілок випуску

Етап **генерації файлів** навмисно не комітить і не надсилає файли проєкту. Після перегляду згенерованого коду створіть або підтвердьте перший коміт у **локальній `main`**. Для повністю порожнього Git-репозиторію спочатку явно виконайте `git init -b main`; інакше працюйте з наявною локальною `main`, включивши віддалені зміни перед налаштуванням.

Коли початкова структура закомічена й робоче дерево чисте:

```sh
python3 .agents/bmforge/manage.py setup-branches --project . --dry-run
python3 .agents/bmforge/manage.py setup-branches --project .
```

Перша команда лише перевіряє; друга, **лише з дозволу користувача**, створює локальні `dev` і `feat/maint-0.1.0` від `main` та переходить у функціональну гілку. Назву можна змінити через `--feature feat/maint-0.2.0`. Початковий коміт, Git push, віддалена гілка, злиття, випуск чи тег не створюються. Менеджер відхиляє неповні/наявні локальні чи відстежувані віддалені посилання, брудні робочі дерева й відсутній коміт `main`, не привласнюючи чужу історію. Надсилайте локальні гілки в `origin` лише за окремим дозволом користувача.

## Повідомлення про оновлення, а не автоматичні оновлення

Використовуйте одну **окрему чисту локальну робочу копію** як upstream-знімок для всіх проєктів. Це дозволяє звичайній перевірці Codex працювати автономно, без доступу до GitHub. Один раз створіть кеш поза Codex:

```sh
mkdir -p "$HOME/.cache"
git clone --single-branch --branch main \
    https://github.com/NadimGhaznavi/bmforge.git \
    "$HOME/.cache/bmforge-upstream"
```

Оновлюйте його **окремо**, коли GitHub доступний:

```sh
git -C "$HOME/.cache/bmforge-upstream" pull --ff-only
```

Робоча копія має лишатися чистою та на `main`. Не використовуйте розробницьку копію BMForge з незакоміченими змінами як джерело перевірки. Встановіть `BMFORGE_SOURCE` або передайте `--source /path/to/clean/bmforge` для іншої копії.

Згенерований `AGENTS.md` просить Codex виконувати **автономну перевірку лише читання** перед першою зміною коду за BMForge в сеансі:

```sh
python3 .agents/bmforge/manage.py check --project .
```

Перевірка порівнює відбитки встановлених навичок із Git-комітом, записаним у кеші. Вона **не** клонує, не отримує, не завантажує й не змінює жодну робочу копію чи файли застосунку. Зміна навички чи контракту повідомляється, навіть коли версія специфікації не зросла; сторонній коміт BMForge **не** створює хибного сповіщення.

Можливі результати: `CURRENT`, `UPDATE AVAILABLE`, `LOCALLY MODIFIED` та `UPDATE CHECK UNAVAILABLE`. Зазначений локальний коміт джерела визначає точку порівняння. **CURRENT означає актуальність відносно кешованого коміту, а не обов’язково останнього коміту GitHub.** Застарілий чи відсутній кеш не дозволяє встановити наявність upstream-оновлень. За потреби оновлюйте кеш окремо.

`LOCALLY MODIFIED` — окреме повідомлення про цілісність: установлена навичка відрізняється від lock-файла, навіть якщо upstream-кеш актуальний. Перегляньте різницю до схваленої заміни. Перевірка не застосовує оновлень.

**Ніщо не оновлюється автоматично.** Codex має повідомити користувача про зміни та запросити дозвіл. Поточний інструмент навмисно **не має команди автоматичного оновлення**. Схвалене оновлення є окремим, перевірюваним кроком зі збереженням локальних змін і закріпленого походження.

**Раніше створені проєкти** зберігають старі менеджер і `AGENTS.md`. Тимчасово зі старим менеджером можна вказати локальну робочу копію явно:

```sh
python3 .agents/bmforge/manage.py check --project . \
    --source "$HOME/.cache/bmforge-upstream"
```

Заміна старих менеджера й інструкцій залишається окремо перевіреним оновленням, а не дією перевірки.

## Перевірка

Використовуйте Python 3 і Git. Для автономних тестів початкового налаштування з BMForge:

```sh
python3 -m unittest discover -s tests -p 'test_skill_bootstrap.py' -v
```

Тести створюють одноразові локальні Git-репозиторії, перевіряють вибір компонентів, сповіщення про оновлення, локальні зміни й відмову від перезапису; вони не збирають DevLog і не звертаються до мережі.
