Зробіть кожен новий проєкт доступним для виявлення CMDB. Під час налаштування визначте назву застосунку, файл констант і шлях встановлення.

Процес відповідає [Налаштуванням виявлення застосунків CMDB](https://github.com/NadimGhaznavi/cmdb/blob/main/pages/app-discovery.md) та окремим посібникам, перевіреним за `/opt/dev/cmdb/pages` 21 жовтня 2026 року. Сканеру CMDB потрібен лише буквальний `VERSION`; BMForge додатково вимагає метадані випуску й корінь встановлення, наведені нижче. Дотримуйтеся [Конфігурації виконання]({{ site.baseurl }}{% link uk/pages/runtime-configuration.md %}) для виявлення налаштувань розгортання через константи та робочий JSON.

## Назва застосунку

Виберіть одну канонічну назву застосунку, що відповідає `[A-Za-z_][A-Za-z0-9_]*`. Пробіли й дефіси не підтримуються виявленням застосунків. Зберігайте регістр назви у файлі констант, а для пакета й каталогу встановлення використовуйте нижній регістр.

| Елемент | Домовленість | Приклад |
| --- | --- | --- |
| Зареєстрована назва CMDB | Канонічна назва застосунку | `MyCount` |
| Назва нового репозиторію | Назва в нижньому регістрі | `mycount` |
| Python-пакет | Назва в нижньому регістрі | `mycount` |
| Робоча копія розробки | `/opt/dev/<lowercase-name>` | `/opt/dev/mycount` |
| Корінь встановлення | `/opt/prod/<lowercase-name>` | `/opt/prod/mycount` |
| Файл констант | `<lowercase-name>/constants/D<Name>.py` | `mycount/constants/DMyCount.py` |
| Клас констант | `D<Name>` | `DMyCount` |

Виявлення обчислює шлях до встановлених констант із зареєстрованої назви. Воно не сканує каталоги розробки й не визначає назву за URL репозиторію. Реєструйте точну канонічну назву через дію **Add Application** у CMDB.

## Оголошення метаданих

Скопіюйте [шаблон констант]({{ '/templates/project/constants/DProject.py' | relative_url }}) до каталогу констант проєкту. Перейменуйте клас і замініть заповнювачі. Зберігайте `VERSION` і `CMDB_CODENAME` як незалежні буквальні рядкові присвоєння в одному рядку; скрипт випуску оновлює їх, зберігаючи анотації й навколишній текст.

| Константа | Вимога |
| --- | --- |
| `VERSION` | Семантична версія без початкового `v`; спочатку `0.0.0` |
| `CMDB_TYPE` | Загальна класифікація; для нових застосунків `"application"`. CMDB приймає інші буквальні категорії без обмеженого словника |
| `CMDB_SUBTYPE` | Короткий опис функції застосунку |
| `CMDB_SUPPLIER` | Назва постачальника; у шаблоні `Nadim-Daniel` |
| `CMDB_CODENAME` | Початковий ярлик розробки; при випуску замінюється повідомленням випуску |
| `BASE_DIR` | Буквальний корінь встановлення `/opt/prod/<lowercase-name>` |

П’ять рядків версії й CMDB мають бути непорожніми, містити не більше 255 символів і не мати керівних символів. CMDB читає буквальні значення на рівні модуля або класу без імпорту файла. Обчислювані вирази, імпортовані значення й читання середовища не підходять. Анотовані присвоєння підтримуються.

CMDB прибирає крайні пробіли чотирьох необов’язкових полів метаданих. Відсутні чи недійсні необов’язкові значення зберігають наявні метадані відповідного випуску. Сумісні спостереження заповнюють відсутні поля; конфліктні метадані вибирають або створюють окреме визначення випуску, захищаючи інші хости. Нова версія містить тільки метадані, які надало спостереження. Зберігайте навмисну класифікацію наявного проєкту, включно з `"Application"`, якщо її зміна не є частиною завдання; регістр не потрібен для виявлення.

## Оголошення постійних даних

`CMDB_COMPONENTS` позначає постійні файлові дані для інвентаризації CMDB та резервного копіювання. Це **не** архітектурні метадані компонентів і специфікацій із [простежуваності специфікацій]({{ site.baseurl }}{% link uk/pages/specification-lifecycle.md %}).

Якщо проєкт не має файлових даних чи баз, використовуйте порожні кортежі. Інакше оголошуйте буквальні пари `(name, value)`, як у MyCount:

```python
CMDB_COMPONENTS = (("Marketing Screenshots", "pages/marketing"),)
CMDB_DATABASES = (("MyCount", "mycount"),)
```

Шляхи компонентів можуть бути відносними до кореня встановлення чи абсолютними. Назви обмежені 255 символами, шляхи — 4096; перехід до батьківського каталогу та відносний шлях `.` не підтримуються. Декларації роблять файлові компоненти видимими для інвентаризації й планування резервних копій у CMDB. Виявлення записує декларацію, не перевіряючи існування шляху.

Підтримуються буквальні кортежі та списки пар, включно з анотованими присвоєннями. CMDB обрізає пробіли назв і значень, нормалізує шляхи й записує дублікати лише один раз. Повторне сканування повторно використовує розгортання; зміни версій зберігають ідентичність розгортань. Змінені шляхи створюють додаткові розгортання, тоді як видалені, пропущені чи недійсні декларації залишають старі. Видалення декларації не очищає інвентар автоматично.

Пари баз даних визначають мітку з’єднання застосунку та точну, чутливу до регістру назву каталогу MariaDB довжиною до 64 символів. CMDB створює нові з’єднання лише для каталогів, які виявлено на тому самому хості. Відсутні каталоги й невдалі читання зберігають попередні з’єднання.

Під час виявлення застосунків CMDB оновлює інвентар MariaDB цього хоста через стандартний локальний сокет, також під час **Add Application** і **Re-Scan Applications**. Декларація дає посилання для виявлення, не створюючи базу даних і не налаштовуючи облікові дані виконання, віддалені хости чи порти.

Каталоги й відповідні бази даних з’являються в панелі Application на сторінці Backups. Резервування каталогів виконується як `cmdbagent`, якому потрібні права читання джерела й запису в призначення. Окремо тестуйте резервну копію, адже виявлення не гарантує успіху: архіви захоплюють живі файли й не гарантують узгодженості застосунку. Посилання на БД використовують наявні політику й історію резервування каталогу. Дивіться [посібник резервного копіювання CMDB](https://github.com/NadimGhaznavi/cmdb/blob/main/pages/backups.md).

## Оголошення мережевих слухачів

Дотримуйтеся [Мережевої конфігурації]({{ site.baseurl }}{% link uk/pages/network-configuration.md %}) для `CMDB_NETWORK`, стандартних значень, робочих перевизначень і перевірки життєвого циклу. Оголошуйте всі власні чи керовані слухачі, включно з внутрішніми та проксі. Для застосунків без слухачів, таких як BMForge, використовуйте порожній кортеж.

## Моніторинг стану застосунку

Дотримуйтеся [Перевірок працездатності]({{ site.baseurl }}{% link uk/pages/health-checks.md %}) для запущених застосунків. CMDB має запитувати **застосунок** через його наявний інтерфейс стану й показувати зелений для успіху або червоний для збоїв і тайм-аутів. Перевірка DB Server виконується всередині застосунку через його налаштоване з’єднання. CMDB **не** повинна відкривати пряме з’єднання MariaDB для цієї перевірки. Опитування й панель стану CMDB плануються окремо; ці специфікації не означають, що вони вже існують.

## Перевірка виявлення

Скопіюйте [перевірку метаданих]({{ '/templates/project/scripts/check-cmdb.py' | relative_url }}) до `scripts/check-cmdb.py`. Із кореня проєкту запустіть зі справжньою назвою й шляхом:

```sh
python3 -B scripts/check-cmdb.py --name MyCount mycount/constants/DMyCount.py
```

Для встановлення використовуйте `--root /opt/prod/mycount` з тим самим відносним шляхом до констант. Локальна перевірка перевіряє метадані, синтаксис задекларованих шляхів і мережеву декларацію, якщо вона є; вона не перевіряє існування каталогів, інтеграцію виконання, робочий JSON, доступність CMDB чи віддалений доступ.

Розгортайте файл констант як читабельний Python-код за обчисленим шляхом, навіть якщо виконуваний файл упаковано. Обліковий запис `cmdbagent` потребує проходження каталогів і читання файла. Облікові дані зберігайте в окремих захищених конфігураційних файлах.

Надайте обов’язкові [Скрипти встановлення]({{ site.baseurl }}{% link uk/pages/installation-scripts.md %}) для послідовного розгортання, оновлення й видалення локального встановлення.

Після встановлення зареєструйте точну назву через Add Application і перевірте хост, версію, тип, підтип, постачальника, кодову назву, шляхи компонентів і з’єднання БД. Add Application ставить у чергу виявлення на інвентаризованих хостах. Після наступних розгортань використовуйте Re-Scan Applications; вона перевіряє інвентаризовані хости без мережевого чи ОС-виявлення й спочатку оновлює їхній локальний інвентар MariaDB.

Перевіряйте повідомлення стану кожного хоста й збережене розгортання, а не тільки `Scan complete`: окремі читання можуть завершитися помилкою після завершення сканування. Відсутні файли, недійсні версії й помилки доступу до хоста зберігають попередні розгортання. Нерозгорнуті визначення й невикористані компоненти очищаються після завдань; нова реєстрація без виявленого встановлення може зникнути після спроби виявлення. Виправте встановлення чи доступ і за потреби зареєструйте повторно. `CMDB_CODENAME` зберігається як тег випуску `VERSION_CODENAME`. Публікація випуску й перевірене встановлення — різні результати.
