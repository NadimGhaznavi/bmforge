# Інженерний контракт

**Перемагає найменша зрозуміла реалізація, що відповідає контракту.** BMForge створено для застосунків, які справді розробляються, а не для уявної корпоративної платформи.

## Обов’язкова поведінка

1. **Реалізуйте лише запитані можливості.** Повторно використовуйте вибрані шаблони та усталені правила проєкту. Не додавайте універсальні фреймворки, брокери, кеші, фонові наглядачі, перемикачі функцій чи іншу інфраструктуру без конкретної вимоги.
2. **Перевіряйте дані на межах довіри.** Перевіряйте недовірені мережеві дані, конфігурацію, облікові дані й повідомлення зовнішніх протоколів при надходженні. Передбачувано відхиляйте некоректні зовнішні запити. Не дублюйте перевірки на всіх рівнях довіреного внутрішнього коду.
3. **Довіряйте внутрішнім контрактам.** Якщо інваріант або перевірений контракт уже встановлено, покладайтеся на нього. Неможливий внутрішній стан — це дефект, а не привід вигадувати резервну поведінку.
4. **Зупиняйтеся швидко й помітно при збої.** Відсутні обов’язкові ресурси, неправильна конфігурація запуску, помилки прив’язування портів і порушені внутрішні інваріанти мають спричиняти зрозумілу помилку та зупиняти відповідну операцію чи службу. Ніколи не імітуйте успіх.
5. **Обробляйте реальні збої розподілених систем.** Для необхідних віддалених операцій використовуйте належні тайм-аути, підтвердження та повідомлення про помилки. Відновлення й повторні спроби мають бути явними, обмеженими та виправданими семантикою операції.
6. **Перехоплюйте винятки лише задля конкретної дії.** Обробляйте відому зовнішню помилку, звільняйте власні ресурси, додавайте корисний контекст або виконуйте визначене відновлення. В інших випадках передавайте виняток далі. Не перехоплюйте все підряд, не приховуйте помилки й не повертайте вигадані значення за замовчуванням.
7. **Тестуйте контракти, а не припущення.** Перевіряйте звичайну поведінку, визначені критерії приймання, важливі збої на межах довіри та потрібні умови запуску й завершення роботи. Обсяг тестів має відповідати складності компонента.
8. **Класифікуйте за відповідальністю.** Дотримуйтеся моделі [Activity / Interface / Entity]({{ site.baseurl }}{% link pages/classification.md %}): класи інтерфейсів з’єднують технології або доступ до доменних даних, класи активностей координують операції, а сутності зберігають значення. Не змішуйте SQL, робочі процеси й стан сутності в одному класі.
9. **Зберігайте схвалені технологічні рішення.** Переліки модулів для компонентів є обов’язковими. [Варіанти візуалізації]({{ site.baseurl }}{% link pages/component-visualization.md %}) також визначаються реальними потребами в графіках, картах чи графах зв’язків, а не вподобаннями Codex. Не замінюйте й не додавайте інфраструктурні бібліотеки, драйвери чи фреймворки без схвалення користувача та оновленої специфікації. Налаштовуйте відомий шаблон, а не перебудовуйте архітектуру.

## Яким має бути збій

| Ситуація | Реакція відповідно до контракту |
| --- | --- |
| Публічний HTTP-клієнт надсилає некоректний JSON | Повернути зрозумілу відповідь 4xx; продовжити обслуговування коректних запитів. |
| Обов’язковий HTTP-порт уже зайнятий | Повідомити про помилку прив’язування й перервати запуск. |
| Внутрішній код порушує встановлений інваріант | Згенерувати змістовну помилку; не продовжувати з припущеними значеннями. |
| Обов’язковий обмін ZeroMQ завершується тайм-аутом | Повідомити викликачеві про збій; повторювати лише тоді, коли контракт застосунку це прямо дозволяє. |
| Транзакція бази даних зазнає невдачі | Відкотити транзакцію й передати помилку далі; ніколи не повідомляти про успішний коміт. |

Перевірка працездатності повідомляє про фактичний стан застосунку; вона не вимагає створювати систему самовідновлення. Дотримуйтеся [перевірок працездатності застосунків]({{ site.baseurl }}{% link pages/health-checks.md %}): один наявний інтерфейс, жодних фонових працівників моніторингу та жодних прямих запитів CMDB до MariaDB. Безпека на відкритих межах є обов’язковою там, де це застосовно, але надлишкова внутрішня валідація не є заходом безпеки.

Кожен новий проєкт також повинен відповідати [контракту життєвого циклу встановлення]({{ site.baseurl }}{% link pages/component-installation.md %}): установлення, оновлення та видалення мають працювати для фактичної топології розповсюдження застосунку. Успішне встановлення залишає читабельний запис про версію та власника у власному каталозі застосунку під `/opt/prod`. Заготовки розгортання **не є доказом** працездатного встановлення.

## Обмеження обсягу роботи Codex

Перш ніж додавати нетривіальну захисну логіку чи додатковий рівень, визначте **вимогу або спостережений збій, який він усуває**. Якщо таких немає, не додавайте його. Краще зрозумілий і помітний збій, ніж код, який мовчки продовжує роботу з помилками.

[Специфікації компонентів]({{ site.baseurl }}{% link pages/component-blueprints.md %}) визначають конкретну поведінку; [відповідність CMDB]({{ site.baseurl }}{% link pages/cmdb-compliance.md %}) та інші наявні процеси регулюють розгортання. Навичка компонента повинна дотримуватися цього контракту, а не замінювати його.
