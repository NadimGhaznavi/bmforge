# Перевірки працездатності застосунків

**Один простий інтерфейс перевірки стану, яким володіє застосунок.** CMDB запитує застосунок, чи здатні його обов’язкові компоненти виконувати свою роботу; CMDB **не** підключається безпосередньо до MariaDB. Перевірка повідомляє стан. Вона не повинна перезапускати процеси, відновлювати з’єднання, повторювати операції чи створювати інфраструктуру моніторингу.

## Що перевіряє CMDB

Для застосунку з HTTP-слухачем використовуйте **GET `/health` на наявному слухачі**. Без нового порту чи сервера.

- Повертайте **HTTP 200**, коли всі необхідні ввімкнені компоненти працездатні.
- Повертайте **HTTP 503**, якщо відомий обов’язковий компонент недоступний. Тайм-аут, недоступна служба або будь-яка відповідь, відмінна від 200, також означає **червоний** стан монітора.
- Повертайте невеликий JSON зі станами компонентів, наприклад:

```json
{"status":"ok","components":{"http":"ok","zmq":"ok","db-server":"ok"}}
```

У разі збою бази даних:

```json
{"status":"error","components":{"http":"ok","zmq":"ok","db-server":"error"}}
```

Включайте лише компоненти, які застосунок справді використовує. Використовуйте `Content-Type: application/json` та `Cache-Control: no-store`. Не розкривайте облікові дані, рядки підключення чи трасування винятків. Реєструйте корисну інформацію про збій на боці застосунку. Відповідь `200` ніколи не повинна містити загальний статус `error`.

`/health` відповідає за **готовність застосунку**, а не лише факт приймання підключень HTTP-сокетом. Окрема точка `/ready` не потрібна без явної вимоги іншої інтеграції; якщо вона є, використовуйте ту саму перевірку.

## Що перевіряє кожен компонент

| Компонент | Мінімальна перевірка | Спосіб виклику |
| --- | --- | --- |
| HTTP-сервер | HTTP-запит обробляється, а застосунок здатний перевірити необхідні компоненти | `GET /health` |
| Сервер ZeroMQ | Наявний обробник REQ/REP відповідає на запит `method: "health"` зі `status: "ok"` | Наявна точка ZeroMQ; застосунок може викликати її для сукупного звіту |
| DB Server | Власний шар доступу до БД виконує один обмежений запит лише на читання через налаштоване з’єднання | Внутрішній метод застосунку, викликаний обробником перевірки; **не** прямий запит CMDB до MariaDB |

Застосунок, що використовує лише ZeroMQ, може надавати стан через наявний протокол ZeroMQ; **не створюйте HTTP-сервер лише для моніторингу**. CMDB потребуватиме сумісного механізму перевірки цієї точки. Інструментарію без постійного процесу чи автономній утиліті не потрібна мережева точка стану.

Перевірка DB Server є **операцією застосунку**. Вона має перевіряти саме з’єднання й дозволи, які використовує застосунок, наприклад `SELECT 1` через менеджер БД. Те, що демон MariaDB працює, не доводить справність підключення застосунку. Не відкривайте спеціального з’єднання CMDB і не оминайте облікові дані застосунку.

## Правила збоїв і перевірки

Зонди мають виконуватися **за запитом, лише читати дані та вкладатися в наявні тайм-аути застосунку**. Без фонового опитування, автоматичного відновлення, універсального запобіжника чи нової служби моніторингу. Для пошуку слухачів використовуйте визначену конфігурацію. Відсутні чи несправні обов’язкові компоненти роблять стан нездоровим; невикористані компоненти опускають, а не позначають несправними.

Перевірте, що звичайний запит повертає `200`, збій обов’язкового ZeroMQ або БД призводить до `503`, а відновлення повертає `200`. Переконайтеся, що у відповіді згадано компонент, секрети не витікають і стан не змінюється.

Це вимоги до інтерфейсу BMForge-застосунків. **Опитування CMDB та кольори панелі — майбутня робота в CMDB**, яка не входить до цієї зміни репозиторію.
