# Специфікації компонентів

Усі реалізації мають відповідати [класифікації Activity / Interface / Entity]({{ site.baseurl }}{% link uk/pages/classification.md %}), [інженерному контракту]({{ site.baseurl }}{% link uk/pages/engineering-contract.md %}), а для запущених застосунків — [перевіркам працездатності]({{ site.baseurl }}{% link pages/health-checks.md %}). Стабільні ідентифікатори, маркери версій і зміни специфікацій описано в [простежуваності]({{ site.baseurl }}{% link uk/pages/specification-lifecycle.md %}).

BMForge — **окремий репозиторій специфікацій та еталонного коду**, а не спільна бібліотека виконання, реєстр пакетів або залежність від фреймворка. Новий застосунок володіє згенерованим чи скопійованим кодом. Не імпортуйте Python-модулі BMForge або інших проєктів у робочий застосунок. Інтеграція між проєктами дозволена лише через явно задокументований публічний API іншого проєкту.

Кожен новий застосунок від початку використовує закріплені стандарти [констант]({{ site.baseurl }}{% link pages/component-constants.md %}), [локалізації застосунків]({{ site.baseurl }}{% link pages/component-localization.md %}) та [життєвого циклу встановлення]({{ site.baseurl }}{% link pages/component-installation.md %}). Константи визначають стабільні програмні ідентифікатори, а каталоги локалізації — текст, видимий користувачеві. Жоден із цих стандартів не додає сервера й не вибирає незапитану технологію.

Бібліотеки візуалізації вибирають відповідно до потрібної **можливості** (графік, географічна карта або граф зв’язків), як описано у [компоненті візуалізації]({{ site.baseurl }}{% link pages/component-visualization.md %}); вони не стають залежностями кожного HTTP-сервера. **Переліки модулів є обов’язковими, а не рекомендаційними.** Розділ **Approved runtime modules** кожного вибраного компонента містить повний перелік технологій для його повторно використовуваної інфраструктури. Codex може підставляти локальні назви, константи та прив’язки, але має зупинитися й отримати схвалення користувача, якщо наявними модулями неможливо виконати вимогу. Довільна заміна сервера, драйвера, ORM, брокера або UI-бібліотеки заборонена. Прикладні активності й окремо схвалені компоненти мають власні залежності.

## Локальні навички Codex у проєкті

Скористайтеся [початковим налаштуванням Codex]({{ site.baseurl }}{% link pages/codex-skills.md %}), щоб установити вибрані навички в `.agents/skills/` застосунку-споживача. Кожна навичка містить відповідний незмінний локальний знімок еталонного коду та чинний на момент встановлення контракт. Закріплені навички не змінюються без схвалення користувача; встановлений менеджер лише **перевіряє й повідомляє**.

Установлення навичок Codex не встановлює сам застосунок. Після визначення вимог навичка **встановлення** зобов’язує Codex завершити й перевірити всі три операції життєвого циклу до першого випуску, із версійним слідом у `/opt/prod` навіть для власної бібліотеки чи програми лише з клієнтською частиною. Незмінний приклад DevLog із поділом ролей використовуйте лише там, де справді потрібна окрема топологія клієнта й сервера.

## Робочий процес Codex

1. Вибирайте лише компоненти, потрібні за вимогами застосунку. Повністю прочитайте кожну специфікацію.
2. Для HTTP і ZeroMQ перегляньте закріплені приклади в `components/reference/bmgeoip/` як **локальні еталонні знімки**, а потім адаптуйте потрібні механізми. Для MariaDB скопіюйте `components/templates/db-server/interface/DbMgr.py` **без змін** і створюйте поверх нього лише необхідні предметні інтерфейси `*Db`. Для Git використовуйте власний окремий шаблон компонента. Ніколи не завантажуйте змінний вихідний код із поточної гілки іншого репозиторію.
3. Замінюйте в адаптованому HTTP/ZeroMQ-коді назви, маршрути, конфігурацію, схему, методи повідомлень, шляхи ресурсів і обробники життєвого циклу, специфічні для BMGeoIP. Не копіюйте бізнес-функціональність GeoIP до стороннього застосунку. Для DB Server передайте конфігурацію застосунку **без редагування канонічного менеджера**. Предметний SQL має бути лише в нових інтерфейсах `*Db`.
4. Перед реалізацією класифікуйте класи застосунку як `activity/`, `interface/` або `entity/` за [контрактом класифікації]({{ site.baseurl }}{% link uk/pages/classification.md %}). Використовуйте композицію, а не вигадану ієрархію класів. Дотримуйтеся наявних процесів BMForge для конфігурації виконання й мережі, встановлення та CMDB. Проєкт володіє власними конфігурацією, службами, тестами, схемою БД і розгортанням.
5. Реалізуйте приймальні перевірки кожної вибраної специфікації. Тестуйте обробку збоїв, запуск, завершення роботи й реальні межі взаємодії. Повідомляйте, що було перевірено та які відхилення залишилися.
6. Точно дотримуйтеся схвалених модулів інфраструктури вибраного компонента. Не додавайте сторонню залежність, не замінюйте схвалену бібліотеку й не створюйте іншу реалізацію через невисловлені вподобання. Якщо модулів недостатньо, зупиніться й попросіть користувача змінити або додати компонент.
7. Уникайте спекулятивної інфраструктури, рівнів, залежностей і функцій. Питайте перед розширенням обсягу.
8. Реалізуйте перевірки працездатності вибраних компонентів через наявні інтерфейси застосунку. CMDB має звертатися до застосунку, а не безпосередньо до бази даних.
9. Помістіть буквальний маркер `BMFORGE_COMPONENT` вибраного компонента в модуль-власник реалізації, використовуючи ID та версію зі специфікації. Це інформація про походження, а не залежність під час виконання чи сертифікат відповідності.

Експорт анімованих GIF окремо описаний у [GIF Animation]({{ site.baseurl }}{% link pages/component-gif-animation.md %}). Цей серверний кодувальник Pillow не замінює Plotly.js і не означає, що кожна браузерна панель потребує генерації GIF.

## Походження еталонних файлів

Приклади в `components/reference/bmgeoip/` скопійовано з `NadimGhaznavi/bmgeoip` на коміті `35c8745c7003a124dce5b5799b08b2d7c851fbfc` (24 жовтня 2026 року). Це незмінні приклади з конкретної ревізії, а не живі посилання; їх не слід періодично синхронізувати без перевірки. Структуру вихідних файлів збережено для демонстрації меж компонентів та імпортів. Деякі приклади залежать від модулів, специфічних для BMGeoIP, які навмисно не входять до каталогу компонентів; агенти повинні замінювати ці інтеграції, а не намагатися запускати знімок як окремий застосунок. Контракт кожного компонента точно визначає схвалені Python-модулі імпорту. Версії сторонніх пакетів установлюються та відстежуються у файлах залежностей **згенерованого застосунку** й оновлюються свідомо.

Компонент візуалізації містить незмінні локальні приклади Plotly/Leaflet із MyCount та Cytoscape із CMDB у `components/reference/`. Його схвалені JavaScript-бібліотеки не залежать від списку модулів Python HTTP-транспорту й потребують явного вибору відповідно до вимог застосунку.

## Межі компонентів

HTTP-сервер відповідає за механіку запитів і відповідей; обробники застосунку — за маршрути, HTML, API та правила поведінки. ZMQ-транспорт відповідає за життєвий цикл сокетів і повідомлень; обробники застосунку — за семантику команд. Канонічний менеджер БД відповідає за механіку з’єднань і транзакцій; один або кілька спеціалізованих класів `interface/*Db.py` — за SQL, схему та відображення записів. `activity/` координує іменовані операції, а `entity/` зберігає дані. Не створюйте залежностей між компонентами без явно потрібного потоку даних застосунку.

**Правило завершення:** компонент вважається доставленим лише після запуску та проходження визначених приймальних перевірок у застосунку-споживачі. Самих документів або скопійованих файлів недостатньо.
